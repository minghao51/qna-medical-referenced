## Implementation

### Existing history seam, no new manager or schema

- `src/infra/storage/interfaces.py` adds `turn(session_id)` and `save_turn(session_id, message, response)` to the existing protocol. The one production implementation and known test fakes implement them; custom injected stores must supply them. No unsafe two-write compatibility fallback.
- `src/infra/storage/file_chat_history_store.py::turn()` uses a separate short-held metadata lock and active-session set. It performs no file I/O, awaits, or lock acquisition on the history-file RLock while admitting/releasing. Same-session overlap raises sanitized `AppError` with status 409/code `chat_session_busy`. Other sessions remain admissible; no global generation queue.
- Both sync and streaming usecases acquire this guard **before history lookup**, retaining it through retrieval, generation, upstream cleanup, and persistence settlement. Streaming releases it **before either terminal is yielded**, so a consumer paused at a success/error terminal cannot leave a completed operation busy. Early generator close/errors/cancellation unwind it.
- `clear_history()` uses the same guard before the existing file lock, rejecting overlap with a turn or another clear. The unchanged history route rotates its cookie only after successful clearing, so rejected clears do not rotate it. A read can inspect the last committed snapshot during generation.
- `save_turn()` appends user/assistant together under the existing file RLock and calls the existing temp-file replacement **once**. Common private append logic retains `save_message()`, TTL, legacy loading, timestamps and message-window behavior. Schema version remains **2**. Both new messages share a timestamp.
- A cap below two rejects pair persistence before mutation/publication rather than storing half the new pair. Existing single-message API/window semantics remain; an odd window may still begin with a retained older assistant message. This is not a pair-aligned history migration.
- Missing files still mean empty history; corrupt-JSON backup/reset and legacy normalization remain. Other read I/O errors now raise sanitized `StorageError` instead of pretending the file was empty and risking overwrite. Write errors omit underlying path/SDK details from their public message. Temporary write failure before publication preserves the existing history file.

### Async commit cancellation and SSE

- `src/usecases/chat.py::_save_turn_async()` first awaits a cancellation checkpoint, then creates one owned off-loop persistence task. **Task submission is admission**, including a job queued for the executor or waiting for the file lock.
- Cancellation observed at the checkpoint submits no job. Once submitted, the worker cannot safely be revoked: shield/drain the owned task, retain session admission until settlement, then propagate the original cancellation. A completed pair may persist; no partial generated fragment is persisted. A worker failure during draining is logged neutrally and does not replace cancellation.
- Drain shields AnyIO level cancellation and tolerates repeated explicit asyncio `Task.cancel()`. There is no request/worker hard deadline: an unresponsive admitted worker can keep its session busy indefinitely. This does not extend to arbitrary independently cancelled child tasks or force-closing the owning event loop.
- `src/app/routes/chat.py` maps **only** known busy errors to a fixed sanitized `chat_session_busy` SSE error terminal with request correlation. HTTP headers already precede stream admission, so busy chat remains **HTTP 200 + SSE error**; busy history clear is **HTTP 409** with the existing JSON error shape and no cookie rotation. No pre-acquired lease in the HTTP handler that could leak if a response generator never starts.
- Existing incremental content, sources, optional trace, single terminal, and error-after-terminal behavior remain. Complete turn history means **server completion**, not proof of delivery/acknowledgment to the browser.
- Touched sync generation logging is neutral instead of logging raw exception/session details. No global logging/privacy/export certification is claimed.
